# 共享核心与四端客户端维护计划

日期：2026-11-15

状态：共享核心基础已实现，后续平台适配与客户端迁移待推进。

## 当前实施进展

已建立 `kotlin-tv/shared-core` KMP 模块，将内容/进度模型、清晰度选择、续播、恢复预算、收藏更新、预加载和定时停止等规则迁入 commonMain。原 JVM core 保留网络、加密、JSON 和线程适配，并通过 api 导出共享核心；现有 Android 已接入。

模块边界和接入说明见 [shared-core README](../kotlin-tv/shared-core/README.md)。本次是阶段 1/2 的核心基础交付；阶段 0 桌面媒体原型、完整账户/播放协调解耦、桌面 UI 和播放器尚未完成。

2026-11-16：新增 `app-desktop` 通用桌面外壳原型，Windows/macOS 共用 Compose 界面，已在 macOS 生成应用包并验证浏览、详情与会话收藏，在线分类接口返回成功。完整桌面 UI 和播放器仍未完成，键盘实机与 Windows 验收待补充，详见 [桌面原型说明](../kotlin-tv/app-desktop/README.md)。

## 目标与范围

在同一仓库中维护一个共享业务核心，以及 Windows、macOS、Android 手机、Android TV 四个客户端。业务规则只维护一份；界面按鼠标键盘、触屏、遥控器分别设计；播放器与系统能力通过平台适配层接入。

本轮不包含 iOS、Apple TV、浏览器客户端，也不新增强制依赖的中心服务。现有 React Native 和 Node 服务是历史实现，不作为本次迁移主线。

## 当前基础

正式 Android 实现位于 `kotlin-tv`，包含 `core`、`app`、`decoder-ffmpeg`。`core` 当前是 Kotlin/JVM 模块，依赖 OkHttp、Java API、Bouncy Castle、Jsoup 和 org.json；部分账户、缓存与播放策略仍在 app 中。

Android 普通构建最低 API 23，legacyAudio 构建最低 API 21。迁移需要保留两条兼容路径，并核验依赖的最低系统要求。保留既有包名、签名、账户数据、收藏和观看进度；禁止依靠卸载重装完成升级。

## 桌面真实播放进展（2026-11-16）

桌面外壳已从布局原型升级为可播放试用版：真实内容和封面、独立 mpv 视频窗口、暂停/跳转/倍速/清晰度、自动连播、本地收藏/历史和续播已接入。本机真实剧集通过播放与控制器验收，应用界面也成功开始播放并暂停。底层使用既有 RemoteVideo 和本机会话 Range 服务，没有替换 Android 播放器。

Windows 代码路径和 CI 配置已提供，Windows 实机播放未验收；账号云同步、内嵌视频窗口、签名更新和长期压力测试仍在后续范围。具体记录见桌面 README。

## 技术选型

| 层次或客户端 | 方案 |
| --- | --- |
| 核心组织 | Kotlin Multiplatform 模块，面向 Android 和桌面 JVM |
| 业务状态 | Kotlin Coroutines、Flow；界面生命周期由客户端管理 |
| 网络 | 先封装现有 OkHttp；有实际跨源集收益时再迁移 Ktor Client |
| JSON | 逐步采用 kotlinx.serialization，保留旧响应兼容测试 |
| 数据持久化 | 先抽象仓储与存储接口；保留旧格式，评估 SQLDelight 后单独决策 |
| Android TV | 保留现有原生 View、焦点导航及 Media3 适配 |
| Android 手机 | Jetpack Compose，独立触屏布局，复用 Android 平台能力 |
| Windows | Compose Multiplatform Desktop，JVM 桌面客户端 |
| macOS | Compose Multiplatform Desktop，与 Windows 共用桌面 UI |
| 桌面播放器 | 独立适配模块，原型对比 libmpv 与 libVLC 后确定 |

四端目前均可走 JVM/Android 路线，因此不为消除所有 Java 依赖而立即重写稳定代码。KMP 提供明确的源集和边界，但不强制第一阶段将一切放入 commonMain。通用纯逻辑进入 commonMain；Java 网络、加密和解析实现暂留平台模块，通过接口注入。具体 Kotlin、Gradle、Compose 和播放器版本在原型验收后锁定。

桌面首批建议验证 Windows x64 与 macOS arm64；Windows arm64、macOS x64 的发布范围在检查实际设备需求及播放器二进制供应后确定，不把可编译等同于已支持。

## 模块边界

建议逐步形成以下逻辑结构，实际目录移动安排在迁移后期，避免与功能迁移混在一起：

```text
shared-core/           模型、业务用例、仓储接口、播放策略与公共测试
platform-android/      Android 网络、存储、安全凭据、Media3 与系统能力
platform-desktop/      JVM 网络、文件、桌面播放器及系统能力
app-android-phone/    手机 UI 和触屏交互
app-android-tv/       TV UI 和遥控焦点交互
app-desktop/          Windows/macOS 共用 UI，平台打包配置分别维护
```

初期可保留现有 Android app 和安装包，在内部划分手机与 TV 界面。是否拆成两个 APK 属于后续发布决策，不在核心抽取时改变包名。

共享核心负责：

- 内容列表、搜索、筛选、详情与选集规则。
- 登录会话业务、收藏、历史、预约、账户与本地数据的合并规则。
- 续播位置、跨集衔接、清晰度选择、地址刷新、预加载预算和重试上限。
- 与平台无关的错误分类、诊断事件和缓存失效规则。

平台层负责：

- 网络传输、密码学实现、安全随机数、设备身份持久化和凭据存储。
- 视频解码、渲染、音频焦点、硬件能力、播放器生命周期和设备兼容。
- 文件、数据库驱动、局域网发现、安装更新和系统生命周期。

客户端负责布局、导航、焦点、键盘快捷键、触屏手势、窗口和页面生命周期。核心不引用 Android View、Compose UI、Activity、Media3 或桌面窗口类型。

## 播放器契约

共享播放协调器发出准备、播放、暂停、跳转、切换源和释放命令；适配器返回准备状态、进度、缓冲、结束、错误和设备能力。状态中带播放会话及剧集标识，忽略旧会话的迟到回调。

播放地址描述需要包含必要请求头、有效期、格式及数据加载需求，不能只暴露一个 URL。诊断输出必须脱敏，不记录账户凭据或可直接访问内容的签名地址。

连播、续播和地址刷新由核心统一决定；平台层报告失败类型并执行设备级恢复。避免核心和播放器分别重试造成请求风暴或重复切集。平台播放器必须能够明确取消加载并释放资源。

桌面播放器原型至少验证真实视频源的请求头、重定向、音视频格式、加密或定制数据加载、seek、倍速、切集、软硬解和资源释放。不能仅以公共 MP4 播放成功决定选型。比较 libmpv/libVLC 的绑定维护情况、二进制体积、架构支持、安装打包及许可证要求后记录决策。

## 分阶段实施

### 阶段 0：记录基线与桌面可行性

记录当前 Android 构建和针对性测试结果，保留真实播放诊断基线。梳理 core/app 依赖，分类为可共享、Android 专用、JVM 可复用。用最小桌面播放器原型验证真实视频源，在 Windows 与 macOS 分别运行。

验收：确认桌面播放可行方案和未解决问题；确定工具链、目标架构及测试设备。桌面媒体链路未通过时，不宣称四端方案已可交付。

### 阶段 1：Android 内部解耦

在原目录抽取业务接口与纯逻辑，界面调用用例，平台实现通过构造参数注入。将旧 Android 实现作为行为基线，逐步迁移播放协调、账户和缓存职责。

验收：现有 Android 构建通过；搜索、登录、收藏、历史、续播和连续播放保持原行为；API 21 兼容构建与普通构建分别验证。

### 阶段 2：建立共享核心和桌面闭环

建立 KMP 模块与 commonTest，Android 接入新核心。桌面先做搜索、详情、播放和观看进度闭环，复用同一套业务用例。按需要替换 JSON 与异步实现，网络库和数据库不同时大换血。

验收：Android、Windows、macOS 调用同一核心业务；错误和取消行为一致；桌面两种系统均完成实际播放、退出与恢复测试。

### 阶段 3：完善四端界面

手机以触屏交互组织页面；TV 保留独立遥控焦点和大屏布局；Windows/macOS 共用桌面页面，补齐窗口、快捷键和系统差异。统一设计语义、颜色与内容模型，不强制共用所有 UI 组件。

验收：四端覆盖搜索、列表、详情、账户、收藏、历史与播放器；TV 完成纯遥控操作，手机完成触屏操作，桌面完成键鼠操作。功能暂缺需在端能力表明确标记。

### 阶段 4：数据迁移与发布

需要升级存储时先提供备份、版本化迁移和失败恢复方案，核验覆盖安装后的账户与进度。Android 延续既有签名更新路径；Windows/macOS 分别实现打包、更新校验及签名流程，macOS 分发同时验证签名、公证与首次启动。

验收：安装、覆盖升级、数据保留、异常退出恢复及回滚策略经过验证。发布产物必须来自通过测试的同仓提交。

## 测试与维护原则

- 公共业务测试覆盖选集、续播、账户隔离、重试上限、取消和迟到回调；使用固定脱敏数据。
- 平台契约测试检查播放器事件、网络失败及存储行为；真实设备验证硬解和长时间播放。
- 播放回归覆盖短时间频繁切集、长时间连续播放、断网恢复、地址失效、切换清晰度和重复进出页面；观察内存、线程与播放器资源是否持续增长。
- CI 按 shared、Android、Windows、macOS 分别构建和测试；公共核心变化触发所有目标验证。
- 一次迁移提交只解决明确边界，避免同时改网络库、存储、界面和播放引擎。旧路径在新路径通过验收后再移除。
- 同仓维护一个核心，四端无需同时发布；发布记录标明核心提交和各端验证范围。没有实际运行的系统不得标为已验收。

## 首个实施任务
